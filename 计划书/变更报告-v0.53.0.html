01起点：一个令人不安的怀疑

v0.51.0 修好了 LLM 栈，真实 E2E 5/5 通过。但有个问题一直没回答：那些修复，保护的是生产环境实际跑的代码吗？

要回答它，我需要一个能判定"这段代码会不会被执行"的工具。此前的做法都很粗糙：

判据问题
import 前缀匹配src.llm 被引用 ≠ src.llm.circuit_breaker 被引用。误报 213 个
谁 import 了这个模块file_processor 被 connectors.py 导入，但 connectors.py 自己无人引用 —— 依然误判为"活的"

正确判据是从入口点做 BFS 传递可达性。我写了 scripts/reachability.py，过程中它自己先崩了一次——因为我算错了相对导入的基准包：

# Python (PEP 328)：`from . import x` 里的 `.` 指向当前模块所属的包
#   普通模块 a/b/c.py      → 所属包 = a.b
#   包       a/b/__init__.py → 所属包 = a.b 自身（不是 a）
非包: base = parts[: len - level]
包  : base = parts[: len - level + 1]   ← 我最初漏了这 +1

漏了 +1 的后果是：每个 __init__.py 里的相对导入都少解析一层，`src/llm/__init__.py` 的 `from .factory import ...` 被算成不存在的 `src.factory` —— 整棵 src.llm.* 被误判为"生产不可达"。修掉后生产可达模块从 275 涨到 429。

最关键的一条我上一轮修错了路径

可达性分析给出一个不舒服的答案：

生产入口 → src/agent/engine.py:203
             → create_llm_provider()

那批修复本身有效（我写了自己的 E2E 覆盖它），但它保护的不是生产实际执行的代码。而真正的生产路径上，藏着一个更严重的缺陷。

02剥洋葱：生产路径上的四个缺陷

一旦把 E2E 对准真正的生产路径（create_llm_provider → chat/chat_stream），问题就一个接一个冒出来。

  1. 第一个：content.split('', 1) ValueError: empty separator

    src/llm/providers/openai.py:128 里分隔符是空字符串——这是编辑操作截断留下的残骸。触发条件是"响应含 <think>"，也就是任何推理模型的思考输出。异常被重试逻辑吞掉 5 次后整次调用失败。

  2. 第二个：BashTool 在 Agent 环路中 100% 失败 RuntimeError: There is no current event loop in thread 'ThreadPoolExecutor-0_0'

    execute() 裸调 asyncio.get_event_loop()，而生产把工具丢进工作线程执行（tool_executor.py:170）。工作线程没有事件循环，异常被吞成"执行失败"。跑测试、git、构建、任何命令全部不可用。

  3. 第三个：.env 可以被 Agent 读取 output 明文含 "OPENAI_API_KEY=sk-***REDACTED***"

    防护代码在 src/utils/path_security.py 里早就写好了，但从未被任何工具接线。读到的内容随后被原样拼进消息，发给远端 LLM。

  4. 第四个：SwarmEngine 构造必然崩溃 ImportError: cannot import name 'create_model_manager'

    该函数在整个仓库中从未定义。而调用方用 except (ImportError, Exception): return None 吞掉它——于是 swarm 自愈路径在线上一直静默失效。

  5. 修完 → 生产路径 E2E 8/8 通过

    含真实对话、真实流式、<think> 提取回归、工具解析、错误传播。

为什么既有测试全绿，缺陷却还在？

tests/test_manual_god_mode.py 在主线程直调 BashTool.execute()。主线程有自动创建的事件循环，所以那条路径永远通过。

同样地，FileReadTool 的测试会检查"能不能读到某个文件"，但不会检查"能不能读到 .env"。缺陷不在测试覆盖的路径上，而在大家默认不会去走的调用上下文里。测试本身写得没错，只是测的不是生产实际走的那条路。

03做了什么

7 个提交。净删 2,377 行。每一条都经真实复现后才修。

3.1 安全：停止泄露密钥

最有效的一处修复是"接线"——防护逻辑已经存在，只是没人调用它。改在四个文件工具的唯一统一入口 path_utils.resolve_path()：

def resolve_path(file_path, base_path):
    resolved = path.resolve()
    if not resolved.is_relative_to(base_path.resolve()):
        return None              # 原有的穿越防护
    if is_sensitive_path(resolved):
        return None              # ← 新增：敏感文件/目录
    return resolved

关键取舍：.env.example 这类模板显式豁免。它不含真实凭据，且是引导新用户配置环境的必需材料——拦掉它只会让人按文档配不起来。

3.2 shell 能力恢复

execute() 现在覆盖三种调用上下文，缺一即该上下文下 BashTool 全废：

上下文处理
无事件循环的线程asyncio.run()
主线程无运行中循环run_until_complete()
已有运行中的循环明确提示改用 async_execute

顺带在工具描述里如实声明能力边界：实现走 shlex.split + 参数列表（无 shell），管道 |、重定向、命令串联天然不可用。不声明的后果是模型写 ls | wc -l，然后拿到一句 ls: cannot access '|' 的困惑报错。

3.3 删除被"遮蔽"的死代码

安静但危险同名包优先于模块

仓库里有 3 处 .py 文件与同名目录并存。实测确认 Python 永远加载目录：

src.core.events       → src/core/events/__init__.py
src.core.git.worktree → src/core/git/worktree/__init__.py
src.llm.model_info    → src/llm/model_info/__init__.py

那 3 个 .py 文件（384 行）永不执行。危害不只是浪费空间：src/core/events.py 与包里的 events/core.py 是两套事件总线实现，而所有调用方拿到的都是包里那份——读代码的人会先看到排在目录前面的 events.py，改完后"改了没效果"。这正是本项目反复出现的缺陷模式。

3.4 三个被静默吞掉的实现缺陷

缺陷为什么测试看不出
create_model_manager 从未定义 调用方 except (ImportError, Exception): return None 吞掉 → swarm 自愈线上静默失效
except TimeoutError 是死分支 Python 3.10 中 asyncio.TimeoutError is TimeoutError → False（实测）。超时落到通用 except，错误码从 E2003 退化成 E2002，超时时间从消息消失
共识规划失败拖垮整个任务分解 该调用位于 try 块之外，而 consensus_planning 默认开启 → 任何 LLM 侧错误都绕过既有的降级契约
