## 3. 新发现的缺陷（本轮实测产生）

### D-01 【P1·工具】`import_sweep.py` 把 `SystemExit` 误判为代码缺陷

- **现象**：`IMPORT-FAIL = 1`，模块 `src.cli.surface_viewer`，错误 `SystemExit: 1`。
- **根因**（`静态确认`，`scripts/import_sweep.py:53-72`）：
  `classify()` 只对 `ModuleNotFoundError` 做第三方/项目内区分，
  其余异常（含 `SystemExit`）一律落到兜底的 `return "IMPORT-FAIL"`。
- **真实原因**：该模块在导入期 `try: from src.core.durable... except ImportError: sys.exit(1)`，
  而 `src/core/durable/surface_manager.py:17` 需要 `jsonschema`（venv 未装）。
  于是"缺一个可选依赖"被上报成"项目代码有缺陷"。
- **影响**：硬指标之一（`IMPORT-FAIL = 0`）**永久性失真**。任何人加一个
  导入期 `sys.exit` 的模块，都会让这条红线变红而无法区分真伪。
- **建议修复**：`classify()` 增加对 `SystemExit` / `KeyboardInterrupt` 的归因——
  若异常发生在导入第三方/可选依赖失败后由项目代码主动退出，归为新类 `IMPORT-EXIT`，
  单独计数、不计入 `IMPORT-FAIL`；并为 `classify()` 补 4 个单测
  （ModuleNotFoundError-第三方 / ModuleNotFoundError-src / TypeError / SystemExit）。

### D-02 【P2·反模式】导入期 `sys.exit(1)` 掩盖真实错误

- 位置：`src/cli/surface_viewer.py:18-28`（`已验证`）。
- 反模式：模块级 `except ImportError: print(...); sys.exit(1)`。
  任何 `import src.cli.surface_viewer` 的调用方（含 import_sweep、未来的插件发现逻辑）
  都会被强制退出进程。
- 建议：改为抛 `RuntimeError`（带原始异常 `from e`），把"从项目根目录运行"的提示
  移到 `main()` 里；文件底部已有 `if __name__ == "__main__"`，无需模块级退出。

### D-03 【P1·环境】没有单一解释器能同时跑运行与测试

- `venv`（3.10.9）：运行依赖齐、**无 pytest / 无 ruff**

- **现象**：`reachability.py --list` 的"连测试都到不了"清单里，第一条是

  （`from src.cli.entrypoint import main`）。
- **根因**（`静态确认`，`scripts/reachability.py:181-186`）：`prod_seeds` 只列了

### D-11 【P2·功能】`undo_multiple_commits(count>1)` 实际只能撤销 1 个

- 现象：连续两个 AI commit 后调 `undo_multiple_commits(2)`，返回
  `(True, "已撤销 1 个 commit")`，第二个撤销被拒。
- 原因（`静态确认`）：第一次 undo 会留下未提交变更，第二次
  `undo_last_aider_commit` → `undo_commit(..., has_dirty=True)` 直接拒绝。
- 影响：`/undo 2` 这类"多级回退"名不副实。
- 现状：已用 `pytest.mark.xfail(strict=True)` 固定该行为
  （`tests/core/test_git_integration_deep.py::TestUndoMultiple::test_undoes_two_commits`），
  修好后 xfail 会自动转红提醒去掉标记。
- 修复方向：在循环内用 `git reset --hard <sha^>` 或先 stash 再连续 reset，
  而不是依赖"每次都必须工作区干净"的 `undo_commit`。

### D-12 【P2·启动】自动初始化 git 仓库的路径会崩，导致 Git 功能静默不可用

- 现象：在**不是** git 仓库的目录里首次构造 `GitManager`，
  `git.Repo.init()` 之后的默认 user 配置抛 `NoSectionError`，
  被外层 `except` 吞掉 → `is_available()` 永久 False。
- 根因（`已验证`）：GitPython 的 `config.get_value("user", "name", default)`
  在 **section 不存在**时抛异常，而不是返回 default。
- 影响：全新项目首次使用 `clawd` 时，`/undo`、`/diff`、commit 归因全部不可用，
  且**没有任何报错**。
- 已修复：`_ensure_repo` 内改用 `_has()` 兜住 `NoSectionError`；
  新增 `test_creates_repo_when_directory_is_not_repo` 锁定。

### D-10 【P1·测试隔离】单进程全量跑到 58% 挂起，分目录跑全过

- **现象**：补装依赖后，`py -3.10 -m pytest tests/ -q` 两次在 **58%** 附近挂起

### 4.1 为什么指标会自相矛盾？

三个独立原因叠加：

1. **度量脚本不在测试保护下**。`import_sweep.py` / `reachability.py` / `coverage_gap.py`
   合计 456 行，**没有任何单元测试**（`静态确认`：`tests/` 下无对应文件）。
   脚本的归因逻辑错了，没有人会发现——D-01 就是这样存活下来的。
2. **环境未收敛**。CI 用 3.11 + `pip install -e ".[dev]"`，本地用 venv(3.10) 或 py(3.14)，
   三者依赖集不同，同一命令得到三种结果。
3. **文档更新粒度是"轮次"而不是"断言"**。每轮只更新自己碰到的数字，
   其余断言原样留着，于是同一文件里 0.51.0 与 0.60.6 并排出现。

### 4.2 为什么覆盖率卡在 46%？

`coverage_gap.py` 给出了答案（`已验证`）：**缺失集中在少数大模块**。

| 模块 | 未覆盖行 | 覆盖率 | 语句数 |
|:---|---:|---:|---:|
| `src.config.generator` | 272 | 15.0% | 320 |
| `src.cli.textual_dashboard` | 223 | 0.0% | 223 |
| `src.tools_runtime.udiff_parser` | 219 | 7.6% | 237 |
| `src.agent.swarm.pipeline` | 207 | 0.0% | 207 |
| `src.workflow.mode_state` | 191 | 45.7% | 352 |
| `src.tools_runtime.watch_tool` | 190 | 14.8% | 223 |
| `src.core.git_integration` | 187 | 26.7% | 255 |
| `src.memory.manager` | 185 | 26.0% | 250 |
| `src.rag.repo_map` | 183 | 49.4% | 362 |
| `src.workflow.pipeline` | 171 | 33.7% | 258 |

**Top 10 合计未覆盖 2,028 行**。全库缺口是 7,766 行（60% 目标 → 33,643 行，当前 25,877）。
也就是说：**做完 Top 10 就能补 26% 的缺口**，且这些模块全部生产可达——
符合"只给可达模块补测"的既定原则。

### 4.3 为什么死模块删不掉？

199 个不可达模块中，134 个"连测试都到不了"（24,667 行）。
历史教训（`ADR-0001`、`workflow_status.md` §0-A）明确记载：
**按名字相似度删除已经误判过一次**。因此只能逐条读代码判定，
每条要回答三个问题：① 有无动态导入（`importlib`/`__import__`/字符串拼接）；
② 有无被文档/配置引用；③ 是否是被"有意替换"的旧实现。
按每条 5 分钟计，135 条约 **11 小时纯判定工作**——这才是它一直没做的真实原因。

### 7.2 静默吞异常统计口径（可复现，两种口径都给）

**权威口径（AST，`scripts/check_silent_except.py`）**：
`except` handler 的函数体只含 `pass` 或 `...` 才计数。

```bash
py -3.10 scripts/check_silent_except.py          # 2026-10-23 实测：172
py -3.10 scripts/check_silent_except.py --baseline 172   # 超过则退出码 1
```

**参考口径（正则）**：

```bash
rg -U --multiline-dotall -c "except[^\n]*:\s*\n\s*pass\b" src/ \
  | awk -F: '{s+=$2} END{print s}'
# 2026-10-23 实测：163
```

> 两者相差 9 处：`except: ...` 占位、以及 `pass` 前夹注释的情形。
> 历史文档里的 206 / 101 是第三种口径（含多目录）。**以 AST 口径为准**，
> 因为它可解释、可测试（`tests/scripts/test_check_silent_except.py` 锁定了语义）。

### 7.3 证据等级使用规则

- 只有实际运行过的才写 `已验证`，且必须附命令与关键输出片段
- 读代码得出的写 `静态确认`，附 `file:line`
- 缺环境的（远端 CI、Docker、gh Release）一律 `待验证`，**不计入完成**

### 8.2 依赖修复后的全量（分四批，因单进程挂起）

补装 `litellm`/`mcp`/`psutil`/`fastapi` 后，单进程全量出现**挂起**（两次：
一次 58% 处进程消失、一次 51%→58% 停滞 5 分钟无进展）。改为按目录分批执行：

| 批次 | 范围 | 结果 |
|:---|:---|:---|
| 1 | `agent core cli llm tools_runtime scripts` | ✅ **1801 passed, 1 xfailed**（96.89s） |
| 2 | `brain cli_handlers contracts integration memory notification performance rag runtime self_healing server` | ✅ **308 passed**（249.73s） |
| 3 | `tests/test_*.py`（15 个根文件） | ✅ **270 passed, 1 skipped**（9.86s） |
| 4 | `test_security test_state utils workflow` | ✅ **822 passed, 4 skipped**（40.12s） |

**四批均 0 failed**，合计 3201 passed / 5 skipped / 1 xfailed
（批次间存在少量路径重叠，各自独立执行）。

### 8.3 未解之谜：单进程全量为何挂起（D-10，待定位）

- 现象：同一套测试，单进程按字母序跑到 **58%**（约第 1836 个用例，
  `tests/runtime/test_engine.py` 与 `tests/scripts/` 交界处）后挂起；
  分目录跑全部通过。
- 判定：**顺序相关**，典型成因是前序测试泄漏了后台线程 / 未关闭的 asyncio 循环 /
  未释放的文件锁——与 `ADR-0006`「测试必须隔离进程级全局状态」直接相关。
- 影响：**CI 若单进程跑全量会超时**（这可能是历史"全量 2806s"的真实原因之一）。
- 定位方法（W3 执行）：二分目录 + `-p no:cacheprovider` 固定顺序，
  找到泄漏点后补 `finally` 清理；不要靠加大 timeout 掩盖。
- 当前规避：CI 与本地一律按目录分批跑，并用 `--timeouts` 类保护（待装插件）。
