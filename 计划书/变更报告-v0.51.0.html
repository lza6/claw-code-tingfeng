一个"文档说能用、实际一跑就崩"的 AI 编程代理框架，是怎么被修回可运行的。

01上下文：起点在哪里

项目自称 v0.45–0.50、覆盖率约 50%、1414 个测试全绿。实测数字不是这样。

19.5%实测覆盖率（自报 ~50%）
563Ruff 违规
213不可达模块 / 46,519 行
306s测试收集耗时

更值得注意的不是这些数字，而是它们的成因。这个仓库的 git log 显示的不是一条演进轨迹，而是四次集成波次——Aider、GoalX、oh-my-codex、ClawGod 各自把源项目的目录结构搬进来，落盘、提交，然后声称完成。

缺的恰恰是最关键的一步：接线验证。没人确认过新代码能不能被运行时的可达路径碰到。当一段代码从未被 import、从未被测试执行过时，它就是化石——静态检查（ruff 的 F821 只查名称不查属性，mypy 未启用）看不见它，覆盖率报告也只是把它算作"未覆盖"而已。

根因三者同源

把上面这些症状串起来，它们出自同一个上游：

缺少可达性契约
   │
   ├─→ 移植代码不接线        → 213 个死模块
   ├─→ 不接线就不进测试      → 覆盖率 19.5% → F821 静默存活
   ├─→ 测试失败用 except 掩盖 → 255 处静默吞异常
   └─→ 文档写"已完成"        → README 虚报覆盖率 2.5 倍

02直觉：为什么必须先跑真实 E2E

如果我只做静态审计，这 11 个缺陷里一个都发现不了。

最初的计划是"按优先级清单逐项修"。清单来自静态分析——那是错的起点。真正的问题只有在把一个真实请求打进去的时候才会一层层剥开。看起来像剥洋葱：每修一层，下一层的错误才露出来。

  1. 接入真实端点，跑最小对话 AttributeError: 'AgentSettings' object has no attribute 'context_window'

    LLM 栈连第一个对象都构造不出来。factory.py 访问了一个不存在的字段——实际叫 max_context_tokens。

  2. 修完字段名，再跑 module 'litellm' has no attribute 'turn_off_verbose_logging'

    依赖版本升级删掉了这个 API，启动路径直接崩。

  3. 修完 API，再跑 401 Incorrect API key ... platform.openai.com/account/api-keys

    请求被打到了 api.openai.com，而不是配置里写的自建端点。根因：_LiteLLMCompatWrapper 构造 litellm 参数时漏传了 api_key 和 api_base。

  4. 修完透传，对话通过了

    但工具调用步骤仍然失败：模型明明返回了 tool_calls，框架却当成普通文本。响应解析只取了 role 和 content。Agent 环路是断的。

  5. 修完解析 → 5/5 全通过

    对话 ✅ 工具调用 ✅ 推理内容 ✅

第二个直觉：写"幂等性"测试，而不是"功能"测试

给配置合并模块写测试时，我没有只测"能不能合并"，而是加了一条重复执行两次结果是否相同。它立刻失败了。

merge_config 无条件把顶层配置追加到字符串末尾。第一次侥幸正确；第二次起，notify、model_reasoning_effort 就落到了 [agents] 表的下面——在 TOML 里这等于把它们变成了 agents.notify。用户每启动一次应用，顶层配置就静默丢失一层。

这条规律贯穿了整轮工作：能暴露问题的不是"这个功能对不对"，而是"重复做会发生什么"、"失败时会不会静默"、"声明的东西真的存在吗"。

03做了什么：11 个阻塞级缺陷

全部经真实运行复现。下面按受损链路分组。

3.1 LLM 栈——此前 100% 不可用

缺陷文件后果
访问不存在的 settings.context_windowsrc/llm/factory.py任何 LLM 创建调用都抛 AttributeError
.env 约定与配置模型字段不匹配src/core/config/models.py按文档配置的用户拿到 api_key=None、模型退回默认 gpt-4

最短的那条修复是配置映射。文档写着 OPENAI_API_KEY，而配置模型用 field_name.upper() 推导环境变量名，只会去读 LLM_API_KEY。两者之间没有任何桥。修复方式是加一层别名解析：

_PROVIDER_ENV_ALIASES = {
    "llm_api_key": ("LLM_API_KEY", "OPENAI_API_KEY", "ANTHROPIC_API_KEY", ...),
    "llm_model":   ("LLM_MODEL",   "OPENAI_MODEL",   "ANTHROPIC_MODEL", ...),
    "llm_base_url": ("LLM_BASE_URL", "OPENAI_BASE_URL", ...),
}

@model_validator(mode="before")
def _resolve_provider_env_aliases(cls, data):
    # 只补齐"缺失"的键，不覆盖调用方显式提供的值
    ...

关键是只补缺失、不覆盖——这样既有部署不会受影响，优先级仍然是「显式传参 > 通用变量 > 提供商专属变量 > 默认值」。

3.2 补丁引擎——Agent 每改一次文件就崩

P0两个方法从未被定义

AtomicPatcher 在 apply_batch 和 apply_changes 里调用了 self.commit() 与 self.rollback()——而这两个方法根本不存在。更严重的是，src/agent/engine_loop.py 在每次文件编辑成功之后都会调用 commit()，失败时调用 rollback()。

也就是说：Agent 每成功修改一次文件，就会抛一次 AttributeError。

同类问题还有三处：被静默覆盖且引用未定义变量的重复 apply_changes；被 apply_single_change 引用却从未实现的 _apply_diff_hunks；自愈引擎调用而类上不存在的 apply_patch。

补齐后，测试从 6 个全失败变为 16 个全通过（新增 10 个回归用例覆盖事务语义、unified diff、上下文不匹配拒绝、语法破坏拒绝、多 hunk）。

3.3 配置包——主入口崩溃

- from src.core.config import get_settings
# ImportError: cannot import name 'get_settings' from 'src.core.config'

src/core/config/__init__.py 只 re-export 了 merger 的内容，AgentSettings、get_settings、load_settings 全部拿不到——而 src/agent/factory.py:70 正是这样导入的。于是 create_agent_engine()（创建 Agent 的主入口）直接 ImportError，且这个异常不在外层 except (KeyError, ValueError) 的捕获范围内。

修复后实测：create_agent_engine() 正常返回 AgentEngine 实例。

缺陷后果

app.add_typer(app, name="setup")形参遮蔽模块级变量，把父应用注册到自身

05没做的部分

这一轮只完成了"止血"，不是全部改造

审计文档里有 8 个波次、200+ 项任务。这轮完成的是波次 1（P0 修复）+ 测试基建 + 文档同步 + 提交推送。明确未做的部分：

  • 死代码收敛——213 个不可达模块（46,519 行）仍在。src/notification/、src/notifications/、src/visual/、src/session_history/ 已人工确认为真死代码，但删除需要逐个人工复核，属波次 2。
  • 覆盖率——仍是 19.5%，pyproject.toml 里 fail_under = 60 与实际差距未消除。爬升路线在文档 §6.1。
  • 结构性重构——exceptions.py 里 16 个异常类各定义两遍（后者静默覆盖前者）等 F811 问题未处理。
  • 性能优化——收集耗时从 306s 降到 126s 是修 __init__.py 的副产品，不是系统性优化。

覆盖率分母的陷阱：删死代码会让覆盖率百分比上升，但那是分母变小造成的假象。真正的指标是已覆盖语句数（当前 9,399），它只能涨不能跌。
