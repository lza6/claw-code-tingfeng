## 第 6 章 根因分析（第一性原理）

### 6.1 为什么指标会自相矛盾？（三个独立原因叠加）

1. **度量脚本不在测试保护下。** `import_sweep.py` / `reachability.py` / `coverage_gap.py`
   合计 456 行，在本轮之前**零测试**。归因逻辑错了没人发现（P2-5）。
2. **环境未收敛。** 三个解释器三种依赖集，同一命令三种结论（§0.2）。目前已收敛到 venv，但文档没跟上（N-1）。
3. **文档更新粒度是"轮次"而不是"断言"。** 每轮只改自己碰到的数字，其余原样留着
   → 同一文件里 0.60.2 与 0.60.6 并排、引用不存在的段落（N-2/N-5）。

→ **推论**：修文档的正确方式不是"再仔细读一遍"，而是**把断言变成可执行检查**（W0' 的 `rg` 断言 + W3 的 CI 门禁）。

### 6.2 为什么覆盖率卡在 46%？

`coverage_gap.py` 给出确定答案（`已验证`）：**242 个生产可达模块 < 60%**，缺口高度集中：

| 模块 | 未覆盖 | 覆盖率 | 语句数 | 测试策略要点 |
|:---|---:|---:|---:|:---|
| `src.config.generator` | 272 | 15.0% | 320 | 生成/覆盖保护/非法输入/幂等 |
| `src.cli.textual_dashboard` | 223 | 0.0% | 223 | Textual `run_test()` 无头驱动，只断言状态文本 |
| `src.tools_runtime.udiff_parser` | 219 | 7.6% | 237 | 正常/空/畸形 hunk/多文件/上下文不匹配 |
| `src.agent.swarm.pipeline` | 207 | 0.0% | 207 | 阶段推进/角色分派/单角色失败/空任务 |
| `src.workflow.mode_state` | 191 | 45.7% | 352 | 互斥/跨会话恢复/并发写/损坏文件 |
| `src.tools_runtime.watch_tool` | 190 | 14.8% | 223 | 变更/去抖/忽略规则 |
| `src.core.git_integration` | 187 | 26.7% | 255 | 提交/回滚/无仓库/冲突/中文路径 |
| `src.memory.manager` | 185 | 26.0% | 250 | 写/检索/schema 版本/并发/重开 |
| `src.rag.repo_map` | 183 | 49.4% | 362 | 建图/增量/大文件剪枝/编码异常 |
| `src.workflow.pipeline` | 171 | 33.7% | 258 | 阶段推进/中断恢复/预算耗尽/失败终态 |

- **Top10 合计未覆盖 2,028 行**（占全库缺口 7,766 行的 26%），全部生产可达。
- 到 60% 需要覆盖 **33,643 行**，即净增 **7,766 行**。**Top10 只能解决四分之一**，
  所以 60% 是**多批次工程**，不是一次冲刺。
- **注意 `src.cli.textual_dashboard`（0%）与 `src.agent.swarm.pipeline`（0%）是整个模块零覆盖** ——
  它们要么是死代码，要么是完全没测的活代码。**W4 第一件事是判定"活/死"，再决定"补测/删除"，
  不要盲目补测可能被删的模块**（这是我最初判断里的一个错误，此处已修正）。

### 6.3 为什么死模块删不掉？

200 个不可达模块中 135 个"连测试都到不了"（24,690 行）。历史教训（`ADR-0001`/`ADR-0004`）：
**按名字相似度删除已经误判过一次**。因此必须逐条读代码，每条回答三问：
① 有无动态导入（`importlib` / `__import__` / `globals()` / 字符串拼接）；
② 有无被文档/配置/脚本引用；③ 是否是被"有意替换"的旧实现。
按 5 分钟/条计 ≈ **11 小时纯判定工作** —— 这是它一直没做的真实原因，不是"忘了"。

### 6.4 为什么全量回归跑不完？

2806s / 3190 用例 ≈ **0.88 s/用例**，但收集只要 5s —— 说明成本在**用例执行**而非导入。
单轮内跑不完 → 实际没人跑 → 回归靠抽样。**这是 P1-1 的根因**，解法不是"更有耐心"，
而是：① 分层测试（快速层 <3 分钟 / 慢速层按需）；② CI 里跑全量（本地只跑快速层）；
③ 用 `pytest -m "not slow"` 标记（需先补 marker 分类，见 W2）。

## 第 7 章 方案对比与推荐

### 7.1 四个候选方案

**方案 A：覆盖率优先（一路补测到 60%）**
集中火力做 W4，用 2-3 周把 7,766 行缺口补掉。优点：`fail_under` 真正生效，质量信号变硬。
缺点：① 当前覆盖率数据已 5 天过期，直接补测可能补在错的地方；② 0% 覆盖的两个大模块可能本来就是死代码，

**方案 B：能力优先（直接做 W6 能力缺口）**
在 RAG 默认启用、流式原生工具调用、eval harness 上并行开工。优点：用户可感知、商业价值直接。
缺点：① 基线不稳，新功能加进去无法证明"没弄坏旧的"；② 现有 433 条 ruff 违规 + 172 静默异常
会在新代码里复制；③ 违背"先让真实可复现"的第一性论证。**风险：功能做完说不清质量。**

**方案 C：度量与门禁优先，然后双线（推荐）**
先用 2 个批次（W0' + W1'，约 1.5 天）把"度量可信 + 文档自洽 + 门禁自动"三件事做实，
再并行开 W4（覆盖率）/ W6（能力）。优点：① 后续所有批次的"完成"都有自动判定，不靠人肉；
② 成本低（1.5 天）；③ 一旦门禁上线，后面每一批都在它保护下。缺点：前 1.5 天"没有可见功能产出"，
对需要向上汇报的场景不友好。

**方案 D：止血 + 一次性全量审计（并行子代理扫描全库，出 21 个问题清单后统一修）**
优点：覆盖面最广。缺点：① 子代理报告与主线程实测已出现过分歧（v0.54.0：子代理称"213 清单方向两个都错"，
主线程实测 255 不可达，量级一致但口径不同）；② 一次性大改违背"外科手术式修改"；
③ 审计产物本身会腐烂（B-2）。**风险：产出漂亮报告，代码没变。**

### 7.2 权衡矩阵

| 维度 | A 覆盖率优先 | B 能力优先 | **C 门禁优先+双线** | D 全量审计 |
|:---|:---:|:---:|:---:|:---:|
| 技术可行性 | 高 | 中 | **高** | 中 |
| 开发成本 | 高（2-3 周） | 高 | **低→中（1.5 天起）** | 高 |
| 维护成本 | 低 | 中 | **低** | 中 |
| 性能影响 | 无 | 中（RAG 默认开启有成本） | **无** | 无 |
| 扩展性 | 中 | 高 | **高** | 低 |
| 风险等级 | 中（可能白干） | 高（基线不稳） | **低** | 中高 |
| 用户可感知度 | 无 | 高 | 低（首 1.5 天） | 无 |
| SaaS 成熟度贡献 | 中 | 高 | **高（前提）** | 低 |
| 可衍生性 | 低 | 高 | **高** | 低 |

### 7.3 推荐：方案 C

**理由（按重要性）**：
1. **只有 C 能在低成本下解决"证据腐烂"这个元问题**。A/B/D 都建立在"证据可信"的前提上，
   而这个前提当前不成立（覆盖率数据 5 天前、test_ledger 无本轮段、evidence/ 无新增）。
2. **C 的产物是"机制"不是"数字"**。门禁一旦上线，后面每个人（和每个 AI）都被它约束；
   而 A 的产物是"46% → 52%"这种下一轮就过期的数字。
3. **C 兼容 A 和 B**：它不排斥覆盖率和能力，只是**先修好尺子再量**。

**C 的显式代价（诚实披露）**：前 1.5 天没有功能产出，且需要用户在这 1.5 天里
接受"提交里只有文档和脚本"。
