### 1.2 一句话结论

**质量的"尺子"已经建成（17 项指标一条命令出数、硬指标全绿），但尺子的刻度长期没跟着实际走
（`fail_under=47` vs 实际 62.39%，静默门禁 172 vs 实际 162，CLAUDE.md 仍写 3261 用例/47.44%），
而当前真正的瓶颈不是"质量不够"，是「能力已写好但没接线（76 模块 / 12,310 行）"
与「接线的前置件本身有缺陷（hook 注册表一点一 spec、状态目录无隔离）」。**

一句话可执行判断：**先把"接线的前置件"修好（M1/M2），再接线（M3/M4），
同时用 T 线把用户可感知的交付面（CLI 噪音、桌面端产物版本、签名、自动更新域名）收口。**

### 1.3 本轮"实际动手跑"发现的 6 个真实缺陷（这是本轮最硬的产出）

> 方法：不看文档、不读旧结论，直接跑命令、看输出、追代码。每一条都有"可复现现象 + 根因 file:line"。

#### F-01 【P1】测试污染真实会话目录 + 渲染层不设防 → `clawd session list` 打印 Mock 对象

**现象**（`已验证`，实跑输出）：
```
$ python -m src session list
sess-20261029_051808  <MagicMock name='mock.goal' id='1176027824'>  1 轮 · tokens 1/0 · $0.0000
sess-20261029_051241  <MagicMock name='mock.goal' id='1157203712'>  1 轮 · tokens 1/0 · $0.0000
...（共 6 行同类）
```
**取证**：`.clawd/sessions/` 下 **22 个会话文件，其中 14 个含 `MagicMock`**；文件内容：
```json
{ "session_id": "sess-20261029_074502",
  "title": "<MagicMock name='mock.goal' id='1271290880'>",
  "messages": [{"role":"user","content":"<MagicMock name='mock.goal' id='1271290880'>"}, ...] }
```
**根因链**（`静态确认`）：
1. `src/core/session_store.py:35` — `DEFAULT_SESSION_DIR = Path('.clawd') / 'sessions'`，**模块级常量、相对 CWD**，
   没有 env 覆盖、没有注入点。
2. `src/agent/engine.py:622` — 会话落盘写 `self.workdir/'.clawd'/'sessions'`；`:618` 用
   `str(getattr(session,'goal',''))` **无条件 str()**，于是 `MagicMock` 被序列化成字符串落盘。
3. 测试里构造的 engine 的 `workdir` 默认就是仓库根 → **跑一次测试就往用户的真实会话历史里写 1 条垃圾会话**。
4. 渲染层（`src/cli/entrypoint.py:563-590` 的 `session list`）不做长度/类型裁剪 → 脏数据直出屏幕。

**影响**：①用户看到乱码即"这工具是坏的"；②真实会话历史被测试污染，`session resume/分叉` 会在垃圾数据上工作；
③每次跑测试都会再污染一次（幂等性缺失）。

#### F-02 【P1】Hook 注册表"一个点只能挂一个 spec"，第二个 hook 静默覆盖第一个

**现象**（`已验证`）：本仓 `hooks/config.toml` 在 `[hooks.PostToolUse]` 下**声明了两个 hook**
（`format` + `lint`），但注册后只有 `lint` 存活，`format` 被静默丢弃，且每次启动打印
`Overwriting existing hook for 10`。

**根因**（`静态确认`）：
- `src/core/hook_registry/registry.py:43` — `_REGISTRY: dict[HookPoint, HookPointSpec]`（**点 → 单 spec**）
- `registry.py:60-64` — 重复注册只 `logger.warning` 后**直接覆盖**；
  而 `:60` 的 docstring 明写 `Raises: ValueError: 如果 Hook 点已被注册` —— **文档与实现相反**。
- `src/core/hooks_config.py:135-163` — 配置语义是「一个 hook_type 下可有多个 hook_name」
  （`for hook_name, hook_def in type_config.items()` 循环 `register_hook`），
  **配置语义（1:N）与数据结构（1:1）不匹配** → 多 hook 天然退化成"最后一个生效"。

**影响**：hooks 是下一阶段**最高优先级的接线目标（2,580 行）**。若先接线再修这个结构，
接上去的每一处都是"看起来配了、实际只跑一个"的假接线——正是本项目历史上反复出现的失败模式。

#### F-03 【P1】`HookPoint(str, Enum)` + `auto()` → 48 个枚举值是 `'1'..'48'`，不可读、不可按名配置

**实测**（`已验证`，直接在解释器里跑）：
```
HookPoint.POST_TOOL_USE  → name='POST_TOOL_USE'  value='10'  (str)
json.dumps({HookPoint.POST_TOOL_USE: 1}) → {"10": 1}
HookPoint.POST_TOOL_USE == 'POST_TOOL_USE'  → False
f"{HookPoint.POST_TOOL_USE}" → "10"
```
**根因**（`静态确认`）：`src/core/hook_registry/enums.py:18` `class HookPoint(str, Enum)` 全部用
`auto()`，str 混入枚举的 `auto()` 得到的是**字符串化的序号**。
**影响**：①日志/审计里全是数字（正是 F-02 那条 warning 的来源）；②任何按名字匹配的配置/外部
hooks.json（Claude Code 生态用 `PreToolUse` 这种语义名）**永远匹配不上**；
③序列化到 JSON/config 后人类不可读，跨版本不可比对。

#### F-04 【P2】每次 CLI 调用固定刷 3 段噪音，且根因是两个 CLI 入口在代码层仍耦合

**现象**（`已验证`，`python -m src <任何命令>` 都会出现）：
```
[INFO] 渠道缓存已初始化 (TTL=3600s, 磁盘=True)          ← loguru 默认输出
Overwriting existing hook for 10                        ← 英文 WARNING，无意义数字
[*] 结构化日志已启用: .clawd\logs\clawd_1793233820.jsonl ← print()
[WARNING] ⚠️ 定价数据已过期 171 天！... (共 5 行)        ← 每次命令都刷
```
**根因**（`静态确认`）：
- `src/cli/entrypoint.py:14` — `from ..main import _register_shutdown_hooks, initialize`
  → 规范入口**复用了历史 argparse 入口的初始化函数**，于是 `src/main.py:100` 的 `print(...)`
  和 `src/main.py:108-110` 的定价检查被带进**所有** Typer 命令。
- `src/llm/channel_cache.py:67` — 模块级 `logger.info`（应为 debug 或延迟到首次真正使用）。
- `src/core/hook_registry/registry.py:64` — 见 F-02/F-03。
- `src/core/cost_estimator/cost_estimator.py:352` — 定价过期文案；`:20` `PRICING_VERSION='2026-04-12-v1'`
  （**171 天未更新 → 成本估算也随之偏差**，与 v0.72.0"成本护栏真正生效"的目标冲突）。

**影响**：CLI 是产品的主界面。每次命令 5~8 行 ASCII 噪音，是"业余感"的最大来源；
而且噪音会掩盖真正的错误行（用户与 AI 都更容易漏掉真错误）。

#### F-05 【P2】桌面端分发产物与源码版本脱节 + 未签名 + 自动更新指向未验证外部域名

**取证**（`已验证`）：
- `desktop/package.json` `version = 0.74.0`，但 `desktop/dist/` 里是
  `Clawd Desktop Setup 0.1.0.exe` / `ClawdDesktop-Portable-0.1.0.exe`，
  `desktop/dist/latest.yml` 里 `version: 0.1.0`、`releaseDate: '2026-10-27T22:02:00Z'`。
- `desktop/package.json` → `build.files = ["electron/**","web/**","package.json"]`，
  `extraResources = host/`（269MB / 14,492 文件）。
- `build.publish = [{provider:"generic", url:"https://updates.clawd.cn/desktop/"}]`，**仓库内无任何签名配置**
  （无 `certificateFile` / `signingHashAlgorithms`）。
- `dependencies` 里仍有 `playwright`（应为 `devDependencies`；虽然 `files` 白名单不会打进 app，
  但会让 CI/部署多装几十 MB，且语义错误）。

**影响**：①用户装到的是 74 个版本前的壳，`app-update.yml` 认为"已是最新"→ 自动更新链路**事实失效**；
②未签名 → Windows SmartScreen 拦截（"未知发布者"），是真实发行阻断项；
③`generic` provider 指向一个**本仓库无法验证归属**的域名 → 一旦该域名被他人持有，等于把更新通道交给外部。

#### F-06 【P1·安全】`hooks/config.toml` 命令以 `shell=True` 执行，且每次 CLI 启动都会加载 CWD 下的配置

**取证**（`静态确认` + `已验证` 加载路径）：
- `src/cli/entrypoint.py:1154-1155` — `main()` 里无条件
  `load_hooks_config(Path.cwd() / "hooks" / "config.toml")`。
- `src/core/hooks_config.py:81-87` — `subprocess.run(cmd, shell=True, timeout=30, cwd=os.getenv("CLAWD_WORKDIR","."))`，
  **无审批、无检疫、无来源标记**。
- 本仓 `hooks/config.toml` 的内容本身在接线后会立刻出问题：
  `PreToolUse.size_guard` 用的是 `python -c ...`（**本机 `python` 命令不存在**，见 CLAUDE.md 解释器矩阵）；
  `SessionEnd.verify` 是 `pytest tests/ -x --tb=short -q`（**每次会话结束跑 ~7-13 分钟全量**）。
- 缓和事实（必须如实写）：`execute_hook()` 目前**没有任何生产调用点**
  （`rg "execute_hook" src/` 只命中定义与 re-export），所以**当前是"加载但不执行"的潜伏风险**，还不是活的 RCE。

**影响**：一旦 M3 把 hooks 接线（这是计划内动作），"`cd` 到任意不可信仓库 → 跑任意 `clawd` 命令 →
仓库里的命令被执行"就成为**活的远程代码执行面**。项目已有 MCP 工具检疫（`src/mcp/governance.py`）
与 `dangerous` 双重确认机制，可直接复用。

## 第 2 章 第一性原理根因分析

> 这一章回答"为什么反复出现同一类问题"。4 条根因各自对应 §3 的成簇缺陷，不是修辞。

### 2.1 根因一：**"增加能力"的成本 < "接线能力"的成本，所以能力永远溢出**

- 客观事实：624 模块 / 135,491 行，但生产入口只走到 478 个（**76 个 / 12,310 行连测试都到不了**）。
- 加一个新子系统（写 8 个模块 + 30 个单测）是**局部、有即时反馈、可独立完成**的工作；
  把它接进 5 阶段引擎需要改 `workflow/engine.py`(1,514 行) 这类热点文件、要跑全量回归、
  要处理"接上之后老路径行为变化"的风险 —— **成本高、反馈慢、容易破坏别人**。
- 于是理性选择永远是"继续加"。四天出 14 个版本（v0.61→v0.74）正是这个激励结构的产物。
- **推论**：接线必须被拆成"单点、可回滚、有独立验收命令"的最小批次（§6 M3/M4 已按此设计），
  否则执行者一定会退回"再加一个能力"。

### 2.2 根因二：**配置层的语义（1:N）与运行期的数据结构（1:1）不同步，且失败是静默的**

- `hooks/config.toml` 的语义是「一个 hook 点下多个 hook」（与 Claude Code / OMX 生态一致）。
- `_REGISTRY` 是 `dict[HookPoint, HookPointSpec]`（1:1），第二个注册直接覆盖。
- 更关键：**覆盖时只 `warning`，不抛错**，而且 docstring 还写着"会 raise ValueError"——
  于是"配置写了但没生效"这件事**没有任何硬信号**，只有一行没人看的英文 warning。
- 这与本项目历史事故同构：`# noqa` 被自动删除→F401 删掉兼容导出（P0）、`fail_under` 放错 section→
  两年没生效。**共同点：错误配置 = 静默降级**。
- **推论**：任何"配置 → 运行期"的边界，都必须有一个**启动期断言**（`validate_registry` 已有雏形，
  但当前 `required_hooks` 默认校验全部 48 个点，实际会把"未注册"当错误 → 需要改成
  "配置里声明的必须全部注册成功"，见 §6 M1-4）。

### 2.3 根因三：**指标有多份手抄副本，而没有"唯一定义 + 引用"机制**

- 同一件事（用例数/覆盖率/可达数）在 `CLAUDE.md`、`README.md`、`skills/clawd-change-workflow/SKILL.md`、
  `.agent/memory/*.md`、`workflow_status.md`、`计划书/*.md` 里**各手抄一份**，且都过时：
  CLAUDE.md 写 `3261 用例 / 47.44% / 可达 ≥443 / 静默 ≤172`；skill 写 `642 模块 / 46.15% / 255 处静默`；
  实测是 `4,964 用例 / 62.39% / 478 / 162`（详见 §12）。
- 后果不是"数字难看"，而是**判断失效**：新人（或下一个 AI）按 47.44% 认为"覆盖率还很差"→
  去做一轮补测，实际早已 62%；按"255 处静默异常"去治理，实际 162 —— 方向与工作量全错。
- **推论**：`.clawd/baseline.json` 已经是唯一可信源，**其它文档只允许引用、不允许写死数字**（§12 给规则）。

### 2.4 根因四：**"相对路径 + 模块级常量 + 无注入点"= 测试与生产共享同一份状态**

- `DEFAULT_SESSION_DIR`、`.clawd/`、`WORK_DIR` 等状态位置大量写成**相对 CWD 的模块级常量**
  （`session_store.py:35` 是典型）。测试没法重定向，于是写进真实目录（F-01）。
- 这类缺陷有一个很坏的属性：**测试全绿**（写盘成功了），只有人肉看 `clawd session list` 才发现。
- **推论**：状态根必须有唯一入口（`CLAWD_HOME`），且 conftest 必须 autouse 重定向 —— 这是 M2 的内容。

## 第 4 章 双线并行方案与权衡

### 4.1 三个候选方案

**方案 A：双线并行（工程师线 M + 体验线 T + 度量线 G 见缝插针）—— 推荐**
M 线先修"接线前置件"（M1 Hook 数据模型、M2 状态隔离），再接线（M3 hooks / M4 swarm+modes）；
T 线并行做用户可感知的收口（CLI 噪音、桌面端产物/签名/更新域名、会话体验）。
两线**文件域不重叠**：M 线动 `src/core/hook_registry/`、`src/hooks/`、`src/agent/`、`src/workflow/`；
T 线动 `src/cli/entrypoint.py` 的显示层、`desktop/`、`src/core/cost_estimator/`。
优点：既解决"能力写得最多但用不上"的主矛盾，又不停掉用户可感知的产出；每个批次都能独立回滚。
缺点：要求严格执行"全量回归 / baseline 取数 / commit"三动作独占串行。

**方案 B：工程收敛优先（先清不可达/覆盖/红线，再谈体验）**
优点：质量信号最硬，`76 模块`、`21,578 行未覆盖`、`374 ruff` 一次性清零。
缺点：一个周期内零可感知产出；且"删到 0 不可达"与既有的 D-13 决策（C 组全部保留待接线）**直接冲突**，
会重演"删掉的是待部署路径"那个已证实的错误方向。

**方案 C：产品体验优先（桌面端做成真正可交付，再回头补工程债）**
优点：用户最快拿到东西（168MB 安装包已存在，只差版本/签名/首启体验）。
缺点：在 P1-1/P1-2（hook 数据模型坏）+ P1-3（状态污染）之上叠 UI，等于把缺陷固化进用户能看到的层。

### 4.2 权衡矩阵

| 维度 | A 双线并行 | B 工程收敛 | C 体验优先 |
|:---|:--:|:--:|:--:|
| 解决主矛盾（能力未接线） | **高** | 中（只降分母） | 低 |
| 用户可感知度 | **高（延迟 1 批）** | 无 | 最高 |
| 质量信号 | 中高 | **最高** | 低 |
| 与既有决策（D-13 保留待接线）一致 | **一致** | **冲突** | 一致 |
| 回滚粒度 | 批次级（每批 ≤1 个域） | 文件级 | 版本级 |
| 风险 | 中低 | 低 | 高（缺陷进 UI） |

### 4.3 推荐与显式代价

**推荐 A（用户已拍板"双线并行"）。**
顺序：`M1 → G1 → M2 → T1 → M3 → T2 → M4 → G2 → M5/M6`。
**显式代价**：第一批（M1+G1，约 1 天）没有任何用户可感知的新功能；
换来的是"后面每一批的接线都不会是假接线"。若跳过 M1 直接做 M3，代价是
"接完 2,580 行 hooks，配置里一半 hook 不生效，且要回头重做注册表"——这条代价已经在本仓
`hooks/config.toml` 上被实测证明（F-02）。
