02三个值得记下的时刻

这一轮的收获不在于改了多少行，而在于三处"如果不多想一步就会做错"的地方。

直觉一：Python 的变量作用域会让一个 `import` 毁掉整个功能

最隐蔽首次运行时指纹永不保存

# src/brain/world_model.py（修复前）
if fp_path.exists():
    try:
        import json          ← 局部导入
        fingerprints = json.loads(...)
    except Exception as e:
        logger.warning(...)

# ... 200 行之后 ...
fp_path.write_text(json.dumps(new_fingerprints), ...)   ← UnboundLocalError

Python 在编译期就把 json 判定为整个函数的局部变量——因为函数体里存在 import json 这一赋值。于是当指纹文件不存在（即首次运行）时，那个分支不执行，json 从未绑定，后面这行直接抛 UnboundLocalError。

这个异常被外层 except 吞成一条 warning。后果是：

首次运行的指纹基线永远不被保存 → 增量索引每次退化为全量重建。而这个模块的文档、类名、方法名全都在讲"基于语义指纹的增量索引"——它的核心卖点，从第一次运行起就没有生效过。

我是怎么发现的：重写一个**过时的测试**时，发现它断言的是已废弃的 API。为了让新断言能跑，我创建了真实的文件让增量路径真的执行——然后它就炸了。

直觉二：抛错类型选错，会把"策略拒绝"送进自愈引擎

集成陷阱异常层级决定谁来处理

审批门禁的第一版实现抛 SecurityError。看起来语义正确——这是安全策略拒绝。

但 engine_loop._execute_single_tool 只捕获 ToolExecutionError：

except ToolExecutionError as e:
    result = ToolResult(success=False, output='', error=str(e))

class SecurityError(ClawdError): ...          ← 兄弟类，不被捕获
class ToolExecutionError(ClawdError): ...

于是异常穿透出去，触发自愈引擎去"修复"一个策略拒绝——而策略拒绝不是缺陷，模型应当看到它并调整策略。改成 ToolApprovalDeniedError(ToolExecutionError) + 新错误码 E2009 后，拒绝变成模型可见的 ToolResult。

直觉三：自动化判据不能授权删除源码

为了清理 163 个死模块，我写了个启发式："存在近名存活模块 → 判为已取代的重复品，可删"。它报出"142 个可删 / 28,806 行"。

抽查第一条就发现误报：

src.core.hook_registry.async_executor  "对照"  src.core.hook_registry
     └─ 后者是同一个包，前者是它的子模块。不是重复品。

src.workflow.worktree_isolation        "对照"  src.cli.commands.workflow_commands
     └─ 仅仅因为名字里都含 "workflow"。

再查一例更危险的：src/hooks/ 与 src/core/hook_registry/ 名字极像，但读源码后确认它们是互补关系——前者是要注册进后者的具体 hook 实现。如果按名字删，会砍掉一整个未接线的功能子系统。

结论名称相似 ≠ 语义重复

基于名称的启发式不足以授权删除源码。我把工具改成"只出复核清单、不判可删"，并把这条教训写进了 CHANGELOG 与跨会话记忆——因为下一次、下一个人都会想走这条捷径。

3.1 审批门禁：PLAN 首次真正生效

在 ToolManager.execute_tool 与 execute_tools_parallel（生产工具执行的唯一咽喉点）按类别拦截：

工具类别PLAN 模式下
read (FileRead/Glob/Grep/HotFiles)放行
write (FileEdit/Write/Patch)拒绝 E2009
exec (Bash/Shell/Command)拒绝 E2009

刻意的范围收窄：只实施 PLAN。DEFAULT / AUTO_EDIT / YOLO 不拦截——因为仓库里没有任何交互式审批设施，DEFAULT 语义中的"需要审批"无法落地，强行拦截会让开箱即用的默认配置直接不可用。

诚实性把"声明了但做不到"说出来

不说明的后果比不支持更糟：用户读到 DEFAULT: 编辑文件或执行 shell 需要审批 会以为有保护。静默的虚假安全感比明说"不支持"更危险。现在 ToolManager 构造时一次性告警，明确告知该模式不会拦截，并给出出路（如需强制只读请设 plan）。PLAN 与 YOLO 不告警——前者是真实施了的，后者的语义恰好就是当前实际行为。

另有一处安全降级方向被刻意锁死：配置读取失败时退回 DEFAULT 而非 YOLO——"读不到配置就放开全部管控"是最危险的降级方向。

3.3 压测暴露的性能瓶颈

压测顺手量出一个数据：200 个并发 bash 调用耗时 19.05s，吞吐仅 11 req/s。定位到 _BOUNDED_EXECUTOR_MAX_WORKERS = 10 硬编码——200 个请求被压成 20 波。

池=10 -> 200 并发 19.05s (11 req/s)
池=64 -> 200 并发 12.40s (16 req/s)   延迟降 35%

改为可用 CLAWD_TOOL_EXECUTOR_MAX_WORKERS 配置，默认值保持 10 不变。诚实说明：收益有限——真正的瓶颈是 Windows 进程创建开销而非线程数，调大池只能缓解排队。

非法配置值（0 / 负数 / 非数字 / 超大）一律回退默认并告警。理由：max_workers=0 会让 ThreadPoolExecutor 直接抛 ValueError，进而让全部工具执行失败——这种低级配置错误不该导致整个 agent 不可用。
