## 一、为什么必须逐条读源码

本项目此前试过**自动化判据**（"存在近名存活模块 → 判为可删"），实测**误报严重**：

```
src.core.hook_registry.async_executor   "对照" src.core.hook_registry
    └─ 后者是同一个包，前者是它的子模块。不是重复品。

src.workflow.worktree_isolation         "对照" src.cli.commands.workflow_commands
    └─ 仅仅因为名字里都含 "workflow"。
```

更危险的一例：`src/hooks/` 与 `src/core/hook_registry/` 名字极像，
但读源码后确认是**互补关系**——前者是要注册进后者的具体 hook 实现。
按名字删会砍掉一整个未接线的功能子系统。

> **结论：名称相似 ≠ 语义重复。自动化判据只能用来缩小复核范围，
> 不能授权删除源码。**

## 四、🔴 一个必须纠正的判断：验证阶段是假的

### 4.1 发现

子代理报告称 `src/workflow/stages/ralplan_stage.py`(256) 与
`ralph_verify_stage.py`(197) 是"真实实现"，而生产 `pipeline.py` 里是
`# TODO … 暂时返回模拟数据`。**前半段属实，后半段的建议不成立。**

主线程核对后的准确情况：

**生产侧**（`src/workflow/pipeline.py`，**可达、在跑**）：

```python
# TODO: 集成 Ralph 循环逻辑
# 暂时返回模拟数据
artifacts = {
    "verification_result": "passed",     # ← 硬编码
    "iterations": 3,                     # ← 也是假的
    "verification_completed": True,
}
return StageResult(status=StageStatus.SUCCESS, artifacts=artifacts)
```

同类桩共 **4 处**（`pipeline.py:342 / 493 / 544 / 587`）。

**未接线侧**（`src/workflow/stages/ralph_verify_stage.py`）：

```python
async def _verify_implementation(self, task, plan, iteration) -> dict:
    # TODO: 实现真正的验证逻辑
    # 模拟验证结果
    return {
        "approved": True,                # ← 简化为总是通过
        "evidence": {"tests_passed": True, "code_reviewed": True},
    }
```

### 4.2 更正后的结论

**两者都是桩。** 未接线的那份只是**循环结构更完整**（有 `while iteration < max_iterations`
与 `approved` 判定），但**循环体同样永远返回 `approved: True`**。
把它接上去，等于用一个更精致的"永远通过"替换一个简陋的"永远通过"——
**不解决问题**。

### 4.3 真正的问题

**"验证"这个能力在本项目里不存在。** 生产管道的验证阶段从不运行任何测试、
不做任何检查，直接返回"通过"。这是最危险的伪实现位置——它不是"缺少功能"，
而是"**谎称功能存在**"。

**建议（超出本次范围，需单独立项）**：
1. 让 `_verify_implementation` 真正调用测试执行器（`tools_runtime` 已有 bash 能力）
2. 或明确把该阶段标为 `SKIPPED` 而非 `SUCCESS` —— 至少不要谎报"通过"
3. 在此之前，任何依赖该阶段结果的自动化决策都不可信

## 六、⚠️ 对第三节"需产品决策"清单的更正

在 import 期就失败** —— 其中多数正是本清单里的"未接线能力"。

**一个连 import 都过不去的模块，谈不上"能力未接线"，它压根不存在可用形态。**
因此"保留还是删除"这个问题在那 16 个身上问错了。
