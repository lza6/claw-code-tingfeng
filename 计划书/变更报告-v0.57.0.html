01上下文：上一轮之后还剩什么

前几轮修的是“会立刻炸”的东西：生产路径的 <think> 崩溃、 BashTool 全量失败、审批门禁是装饰性的、验证阶段撒谎说“通过”。 这一轮面对的是另一类问题——不会立刻炸，但一直在悄悄误导你的东西。

表面症状

clawd agent 和 clawd workflow 两个命令组根本不存在。
但 CLI 启动没有任何报错，所以没人发现。

根本原因

try: … except ImportError: pass。
本意是“可选模块缺失时优雅降级”，实际把硬错误吞成了静默消失。

更深的症状

40 个名字在代码里被使用，却从未被导入。
其中 7 处位于真实运行路径上，一走到就 NameError。

最隐蔽的症状

一个 dataclass 的字段被同名 classmethod 覆盖， 导致 snapshot.ready 是个方法，if 判断恒为真。

02直觉：为什么这些问题能活这么久

因为它们全都不违反任何单点检查：

  1. 导入失败被 except 吃掉了，所以“能启动”。
  2. 未定义名称只在那一行执行时才炸，静态检查没开 F821。
  3. 重复定义的“后一份”覆盖“前一份”，程序照常运行——只是前一份是死代码。
  4. 测试文件从初始提交起就引用不存在的 API，所以它从来没绿过， 也就没人把它当作信号。
  5. 可达性分析只看“有没有 import 链”，不看“import 到的东西能不能加载”。
共同模式：所有检查都只问“它是否存在于某处”， 没有一条问“它是否真的可用”。这就是这一轮要补的那条缝。

03做了什么

3.1 让降级可见，而不是静默

# 之前：任何导入错误都被吃掉
try:
    from .commands.agent_commands import register_agent_commands
    register_agent_commands(app)
except ImportError:
    pass

# 之后：降级保留，但必须留痕，并把失败清单交给测试断言
try:
    ...
except Exception as exc:
    failed.append(group_name)
    logger.warning("命令组 '%s' 注册失败…%s: %s", group_name, type(exc).__name__, exc)

3.2 把“可达”升级为“可导入”

新增 scripts/import_sweep.py：逐个 import 全部 638 个模块， 并把 ModuleNotFoundError 分成两类—— 缺失名是 src.* 的是项目内路径配错（真缺陷）， 缺失第三方包（celery、opentelemetry）的是环境问题（不算缺陷）。 混为一谈会制造大量假问题。

等级缺陷后果

3.4 一个刻意“不修”的决定

src/agent/swarm/coder_agent.py 引用了 .consensus， 而 consensus.py 在 git 全历史中从未存在。 它零消费者、未导出、从第一天起就无法导入。

选择删除，而不是补写一个 consensus.py。 因为补出来的只会是一个“能导入、但验证永远通过”的桩—— 这正是上一轮刚刚清理掉的那类伪实现。

3.5 顺带闭合的三条调用断链

修完静态缺陷后继续顺链路追查，又发现三处“界面有、后端没有”：

断链真实表现修复
顶层 workflow 命令 vs 同名命令组 命令组遮蔽命令，clawd workflow "目标" 把目标当子命令解析 顶层命令改名 run
--dimension/-d CLI 写入运行时配置后，全仓库无人读取，参数被遗忘 引擎解析 → 注入执行器提示词 → 挂到任务并持久化
两个 CLI 入口并存 python -m src.main 与 clawd 命令集不同、workflow 语义不同 新增 src/__main__.py，python -m src 与 clawd 一致

3.6 一个被数据推翻的“优化”

RAG 增量扫描原本比纯串行还慢：1000 个缓存命中的文件，却要付 1000 次 线程池调度和 1000 个 coroutine 的开销。 

全量扫描        13.20s
纯串行缓存命中   0.73s
原增量扫描       2.20s   ← 并行反而更慢
改后增量扫描     0.70s

结论：并行只在“工作量大到能摊薄调度开销”时才划算。 缓存命中是 O(1) 的 stat，不需要线程池。

3.7 v0.57.1 补充：启动耗时与一个被掩盖的循环导入

发布后继续追可用性，发现 litellm 在导入期就被加载（单次约 34 秒）， 而它在一条很深的依赖链末端： 

src.main → cli_handlers → workflow → experience_bank
  → enterprise_ltm → litellm_singleton → litellm

于是 clawd --version 也要等几十秒。四处改为惰性导入后：

命令之前之后
import src6.8s1.6s
import src.main50.9s~8s
更重要的发现：惰性化把一个被导入顺序掩盖的循环导入暴露了出来 —— src.utils → src.core → src.rag → src.utils。 受影响的是以 from src.utils import ... 作为进程第一个导入的任何调用方， 包括 CodeGraph.build 的进程池子进程（实测抛 BrokenProcessPool）。

第一版修复把整行 logger 导入提前，结果 .debug 子模块把 utils.debug 覆盖成了模块对象，调用时报 TypeError: 'module' object is not callable，全量测试 56 红。 最终改为“只提前绑定 get_logger”，完整导出仍保持在 .debug 之后。
